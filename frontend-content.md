## 3. The Problem

### MCPs are powerful. Getting them running is still a hassle.

Found an MCP server on GitHub? Now comes the setup.

Clone a repository. Install dependencies. Configure environment variables. Set up authentication. Add the server to your client. Repeat for every integration.

And when you're building an agentic application, you have to solve many of these problems all over again.

MCP should make tools easier to use, not harder to connect.

## 4. The Solution

### One place for your MCPs. One foundation for your agents.

Discover available MCP servers, connect the services you already use, and manage authentication through a consistent interface.

Building your own agentic infrastructure? Use the same underlying tooling through APIs and SDKs instead of implementing discovery, authentication, and credential management from scratch.

**For users:** Find and connect tools without the usual setup overhead.

**For developers:** Build agentic applications on reusable MCP infrastructure.

## 6. For Developers

### The infrastructure layer your agents are missing.

Building agents means connecting models to tools, services, and user identities. Each integration brings its own authentication and credential requirements.

Build on a shared foundation instead.

**MCP Registry**

Discover registered MCP implementations and their metadata.

**Authentication Layer**

Support platform OAuth, organization-owned OAuth applications, and existing service credentials.

**Controlled Secret Access**

Let MCP implementations request authorized credentials through a shared provider instead of accessing secret storage directly.

**JavaScript and Python SDKs**

Integrate MCP discovery, connections, and access into your own applications.

**Composable Architecture**

Use the shared abstractions to build and run MCP implementations without coupling them to a specific credential backend.

## 7. Authentication

### Your tools. Your accounts. Your choice.

Different integrations need different authentication methods. The infrastructure should support them without forcing developers to build each flow themselves.

**Platform-managed OAuth**

Authorize supported services through the platform's configured OAuth integrations.

**Bring your own OAuth**

Use your organization's own OAuth application credentials.

**Existing service credentials**

Reuse supported API keys or tokens from applications you already have, with access controlled by the configured permissions.

Authentication stays separate from the MCP implementation.
